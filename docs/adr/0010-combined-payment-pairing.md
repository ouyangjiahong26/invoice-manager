# ADR-0010: 合付配对与智能体金额修正归一

日期：2026-10-05　状态：已接受

## 背景

- 真实批次出现合付场景：京东一次下单拆成多张发票（161.00 + 254.94 + 81.16 = 497.10），微信只付一笔 496.96（商家优惠差 0.14）。规则 3 只做单张发票组对单笔支付组的两两总额比对，配不上。LLM 兜底提示词没告知“一笔支付可对应多张发票、金额允许小额差异”，实测时配时不配。
- 更严重的是配对智能体在线上直接 500：`agent-round` 重读修正把 LLM 原始 JSON 的 float 金额（如 `496.96`）写进 records，第二轮 `pairing.pair` 里 `Decimal("0") + float` 抛 `TypeError`。DEBUG=False 下 Django 默认日志的 console handler 带 `require_debug_true` 过滤器，异常零日志，只能从 nginx 状态码发现。

## 决策

- 规则 3 扩展为组合配平：枚举单边发票组的组合总额与单边支付组总额比对（容差不变）。组合与支付各不被其他匹配占用时直接并成一组。同一发票或支付落入多个匹配时连通后整体进待确认组（沿用 ADR-0006“任一侧多候选进 pending”）。发票侧组件超过 15 个时退化为单张比对，不枚举子集。
- 小额差异仍交给 LLM：确定性规则只认总额相等。优惠、立减造成的几元内差额由 `group_suggest` 结合商家、商品摘要判断，提示词明示合付场景与小额差异的容忍边界。`pair_summary` 补充 `items_summary`（支付截图常含“京东-订单编号”这类商家线索）。
- LLM 组形状校验：`llm_merge_groups` 丢弃缺发票或缺支付的 LLM 组。此类组无法提交，退回未配对走单边发票组流程更诚实。
- 金额入口归一：`pairing.pair` 入口把 int/float/数字串统一转 Decimal（解析失败按缺金额），`agent-round` 重读结果先过 `decimal_or_none` 再合并。修复 500 并杜绝同类混算。

## 后果

- 修订 ADR-0006 规则 3 的“单边发票组与单边支付组总额相等”表述：现为“组合总额配平”，语义为原规则的扩展而非推翻。
- 组合多候选（如单张 100 与 30+70 都配得上支付 100）从“自动成组 100 那对”变为整体待确认。有歧义时交人，不再猜。
- 线上 agent-round 500 消除。如需在 DEBUG=False 下看到未处理异常，后续可单独配置 `LOGGING`（本 ADR 不展开）。
