# ADR-0015: 每用户建批数量上限

日期：2026-10-30　状态：已接受

## 背景

管理员与自助组成员都能创建批次。此前建批没有数量限制，单个账号可以持续创建批次，占用数据库记录，也可用来对服务器施压。批次创建人从 ADR-0014 起记录在 `Batch.created_by`，为按用户计数提供了依据。

## 决策

- 每个用户创建的批次总数上限为 100，集中定义在 `core/access.py` 的 `MAX_BATCHES_PER_USER`。
- 计数范围是 `Batch.created_by` 为该用户的全部批次。已存档批次计入，删除批次后名额释放。历史批次创建人为空，不计入任何用户。
- 看板新建批次和 Django 后台新增批次共用同一校验。自助组成员通过看板建批，与管理员走同一入口。
- 后台新增批次时 `created_by` 为空则记为当前操作人，再按该用户计数。
- 校验在事务内锁定用户行后计数并创建，同一用户的并发建批串行执行。生产数据库为 PostgreSQL。
- 达到上限后不创建批次，页面提示包含上限值。管理员提示删除旧批次后再试，非管理员提示联系管理员清理旧批次。归档不释放名额，提示不把归档列为释放方式。
- `import_batch` 不检查上限，但其创建的批次计入执行人的数量。

## 后果

- 上限是硬上限。归档批次仍占用名额，释放名额需要删除批次。含条目的批次受 `Item.batch` 的 `PROTECT` 约束，需先清空条目才能删除。
- 管理员和自助组成员都受同一上限约束，不按组或全局另设上限。
- 上限值调整只改一个常量，页面提示与后台校验随之变化。
- 默认测试库 SQLite 不支持 `SELECT ... FOR UPDATE`，并发场景的行锁只在 PostgreSQL 上验证，测试用 `skipUnlessDBFeature` 跳过 SQLite。
