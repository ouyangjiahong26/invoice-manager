# ADR-0005: 条目附件改为多附件模型，号码与金额下沉到附件

日期：2026-09-28　状态：已接受

## 背景

真实报销材料（参考 2026-09-24 实验班报销）里存在多种结构：

- 一张发票对应多笔支付（1 发票 ↔ 5 支付）。
- 一笔支付对应多张发票（京东拆单 67.70 + 80.70）。
- 快递费单独开票（50.90 书价 + 6.00 物流费）。
- 退款后净报销（实付 199、退回 20、报销 179）。
- 发票金额 ≠ 实付款（商家优惠立减）。

旧模型每条 Item 只有 `invoice_file`、`payment_screenshot` 两个文件字段，发票号码与支付订单号直接挂在条目上，无法表达上述任何一对多关系。

## 决策

- 新增 `Attachment` 表：`item` 外键、`kind`（invoice/payment/refund）、`file`、`amount`、`order_no`、`merchant_no`、`invoice_no`、`ocr_data`、`created_at`。一条目多张附件。
- Item 删除 `invoice_file`、`payment_screenshot`、`invoice_no`、`order_no`；`actual_amount`、`invoice_amount` 保留，语义收窄为净实付款与发票合计，可由附件合计自动回填、也可手改。
- 数据迁移（`0004_item_attachments`）按"先建表 → RunPython 搬数据 → 删旧字段"执行；文件只复制 `FieldFile.name`，不搬物理路径（storage 照常打开旧相对路径）。
- 号码与金额下沉到附件，因为同一条目里不同发票的号码不同、不同支付的单号不同。
- 快递费发票不单独建模：`kind=invoice`，金额合计校验天然覆盖。
- 提交页上传前用 `URL.createObjectURL` 预览、已保存附件走鉴权路由；图片用 `<img>`，PDF 用 `<iframe>` 交给浏览器原生渲染，不引入渲染依赖。
- 识别与校验：附件金额/号码由 DeepSeek 识别回填（发票、支付、退款三套提示词），金额合计与单号互配在页面实时核对，服务端 `check_item` 继续以警告形式兜底。

## 取舍

- **不采用固定第二组字段**（`invoice_file2`、`payment2`…）：数量不定，字段会不断膨胀，且无法表达"这笔支付属于哪张发票"。
- **不为快递费、退款建专门模型**：它们与普通发票/支付只在语义和净额计算上有差别，用 `kind` 表达足够；专门模型会带来一套平行规则。
- **Excel 单元格超链接只指向每类第一张附件**：多张完整材料走 zip 导出。若管理员反馈不够，后续再加聚合页。

## 后果

- 导出 zip 文件名带类型与序号：`类别_序号_付款人_发票/支付记录/退款记录_N.扩展名`。
- 校验、留痕、导出的金额口径统一改为附件合计；`check_item` 去掉 `prefill_data` 参数，抬头/税号从发票附件的 `ocr_data` 读取。
- 旧数据迁移后附件文件仍在原 `invoices/`、`payments/` 路径，新上传走 `attachments/%Y%m/`。
- 迁移不可逆：旧 `order_no` 是非空字段，反向无法还原，回滚需从数据库与媒体备份恢复。
