# ADR-0006: 批量配对提交（攒批材料一键识别）

日期：2026-09-28　状态：已接受

## 背景

- 学生的实际报销习惯是攒一批材料一次性处理：同一批里多张发票、多笔支付、若干退款混在一起。
- 逐条提交要求上传前先人工想好"这条对应哪张发票、哪笔支付"，材料一多就容易分错、漏配，且要来回多次提交。
- 配对原料已经存在：发票备注单号 ↔ 支付平台单号/商户单号的互证（单条页与 `check_item` 已在用）；自动识别已能提取三类票据的字段；但发票识别此前不提取商品内容，无法建议明细。

## 决策

- 新增独立批量页 `/items/batch/`：单栏混合上传（`multiple`），逐张串行调 `vision.detect`（一次模型调用判类型 + 提字段）；文件由前端持有、识别不落库（对齐 prefill 的无状态哲学，服务端不暂存、无清理问题）。
- 配对在服务端执行、规则优先：`core/pairing.py` 纯函数，按序执行——
  1. 单号互证：发票备注单号 = 支付平台单号/商户单号 → 同组，同单号多张多笔并入，冲突并组（并查集）；
  2. 退款挂组：退款单号命中任一支付同名字段挂入，挂不上时金额与唯一组的支付合计相等兜底；
  3. 金额兜底：单边发票组与单边支付组总额相等且双侧各唯一候选才成组，任一侧多候选进"待确认组"；
  4. 剩余进"未配对"，逐张带原因。
- LLM 只做兜底：规则配不上的记录摘要交 `vision.group_suggest` 归组；成组后交 `vision.field_suggest` 按类别表建议明细文案与类别（发票提示词新增 `items_summary` 提供素材）。两者失败静默降级（未配对提示/确认页手填），不阻断。
- 预览页人工确认：分组、待确认、未配对三区；支持移出成员、待确认组并入目标组、未配对手动加入某组、忽略文件；明细/类别为 AI 建议可改，实付/发票金额自动按组合计预填。
- 提交事务性：`batch_submit` 逐组校验必含发票+支付、文件合法（复用 `validate_upload`）、金额可解析；任一失败整体 400、不建任何条目；成功一次性创建 N 条 `pending` 条目，沿用 `check_item` 聚合警告与 `mark_attachments` 创建留痕。
- 识别服务未配置时页面隐藏上传区并引导单条提交。

## 取舍

- **不在前端复刻配对规则**：规则唯一实现在 `pairing.py`（零 Django 依赖，可独立单测）；前端只做展示与人工调整。
- **不建中间模型或暂存表**：文件由前端持有，分组计划以 plan JSON 随 multipart 一次性提交，避免服务端暂存文件的生命周期管理。
- **未配对不生成条目、单边组拒绝提交**：与"警告不阻断"哲学的边界——金额不一致、缺平台单号是提醒可修复的疏漏，而配对缺一方属于材料本身的硬缺失，生成残缺条目只会污染看板。
- **改类型重识别复用现有 `/items/prefill/` 端点**，不改其契约；每批调用量 = N 次文件识别 + 至多 2 次批量调用（成组、字段建议），识别由前端串行发起。
- **LLM 配对错配由用户在预览页纠正**，服务端不做二次校验；`batch_submit` 只校验单边组与文件合法性。

## 后果

- `vision.prefill` 的 `_prefill_image`/`_prefill_pdf` 参数化接收提示词，`detect/group_suggest/field_suggest` 复用同一请求与解析路径；`_parse_content` 抽出 `_load_json` 围栏剥离。
- `views._new_attachment` 抽出 `_build_attachment`（按字段 dict 构造附件），单条表单与批量 plan 共用金额解析、截断与 ocr_data 逻辑。
- 单条提交页不展示 `items_summary`（多余键无害）；批量页把它作为明细建议素材与卡片摘要展示。
- 规则 3 的金额兜底按"发票金额 = 支付金额"比较，不扣退款；退款先按单号/金额挂到支付所在组后随组参与后续配对。
